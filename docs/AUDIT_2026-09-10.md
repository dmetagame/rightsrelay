# RightsRelay audit — September 10, 2026

Audited application commit: `f27448ae54705c6d98cf2e77ed868cce112890f3`.
Audited deployment commit: `23d2f9fd39700244a561b99b482c6f41e99c7539` on `gh-pages`.
Scope: Python policy, models, Sibyl integration, exports, CLI, console, x402,
ACP Python/TypeScript adapters, tests, dependencies, repository hygiene,
deployed static site, and hackathon submission evidence.

## Assessment

The central memory-dependent release flow works. The existing suites pass,
and a new offline rehearsal proved recall after a real SIGTERM/restart and
BLOCKED/no packet followed by CLEARED/packet after an explicit offline grant.
However, the implementation has significant gaps in console truthfulness,
action authorization, payment recovery, and ACP completion handling. It is
not ready for unrestricted production use. The earlier blanket recommendation
to stop all development was premature: the findings below deserve targeted
repairs and regression checks before the final recording.

No application source, live authorization, wallet configuration, or partner
lifecycle was changed during this audit. No payment, signer operation, ACP job,
or public-site mutation endpoint was exercised. Reproduction probes used
temporary databases and offline CLI actions; all such databases/processes were
cleaned up. This report and the project handoff are the only repository edits.

## Findings, ordered by repair priority

### F01 — High: ACP can complete on-chain but never return success locally

Locations: `acp/runner.ts:195`, `acp/runner.ts:203`, `acp/runner.ts:119`.

The SUBMITTED branch recovers an absent API deliverable from Sibyl plus the
verified JobSubmitted hash and calls `session.complete()`. On the next poll,
the COMPLETED branch requires `session.job.deliverable` from the API again.
When it is still absent, the loop continues until timeout rather than emitting
the successful result. The recovered value is not retained or reused there.
The installed SDK's `JobSession.fetchJob()` replaces the job from the API;
`complete()` does not fill its deliverable field. This is the same API omission
documented during the real job, not a newly invented network failure.

Evidence: source/installed-SDK tracing; the full paid lifecycle was not rerun.
The current delivery unit test checks the hash helper, not this completion
transition. The fallback also searches only the most recent 2,000 blocks, so a
delayed resume can lose access to older submission evidence.

Repair: retain or revalidate verified delivery through COMPLETED, including
restart recovery, and test SUBMITTED → COMPLETED with the API deliverable
absent throughout. Preserve exact job/provider/hash verification.

### F02 — High: console actions accept unauthenticated cross-origin requests

Location: `src/rightsrelay/console.py:186`.

The POST endpoint dispatches mutations and purchase commands without an
operator token, Origin/Host validation, or CSRF protection. A temporary ASGI
probe sent a form-compatible POST with `Origin: https://untrusted.example` to
`/actions/init-aurora`; it returned 200, CLI exit 0, and created the entity.
The endpoint requires no request body or custom header. A caller able to reach
the local service can invoke its fixed actions; a browser's private-network
restrictions may affect browser exploitability, which was not tested here.
Binding to loopback by default reduces exposure but is not application-level
authorization. The `--host` option also permits wider binding.

Impact includes overwriting authorization and invoking x402 when the launcher
inherits funded credentials. The public GitHub Pages site does not expose this
service. No funded action was called during the audit.

Repair: protect the operator action boundary and reject untrusted origins;
test both authorized actions and rejected cross-origin requests.

### F03 — High: the board can display CLEARED without an authorization

Locations: `src/rightsrelay/console.py:100`, `src/rightsrelay/console.py:115`,
`src/rightsrelay/console.py:130`, `src/rightsrelay/console.html:258`.

The status projection lets the newest journal event override the current
authorization even when that authorization is missing. In a temporary DB,
after applying a grant and deleting only the WARM entity, `/status` reported:
`entity_found=false`, `status=CLEARED`, `authorization_status=PENDING`, and
empty reasons. The underlying export still fails closed; the board does not.
On a status-fetch error, browser code also retains the previous green status
and advances its locally extrapolated clock, changing only the small log text.

A second probe exported organic YouTube, then attempted blocked paid Instagram.
The board reported `BLOCKED` and `packet_written=true`; the file contained the
old YouTube attempt. `packet_written` only checks filesystem existence, without
binding the packet to the current attempt or authorization version.

Repair: make unavailable authorization visibly non-cleared, mark stale status
as disconnected, and distinguish a historical packet from a valid packet for
the current attempt. Preserve earlier artifacts as history if desired; do not
treat them as evidence of the latest blocked release.

### F04 — Medium: ordinary initialization can erase purchased rights

Locations: `src/rightsrelay/app.py:99`, `src/rightsrelay/app.py:126`.

`init-aurora` unconditionally overwrites the one entity with PENDING/version 1.
The probe changed a CLEARED/version 3 authorization with paid scope into
PENDING/version 1. Any existing ACP job ID, transaction reference, and evidence
references are cleared by construction. This action is always available as a
console button. `review-limited` also unconditionally replaces the scope, and
can downgrade a paid grant while preserving its earlier transaction/job fields.
The ACP-specific mutation has guards against this, but the local reviewer does
not. Journal entries are not deleted, although they do not contain the full
prior authorization scope needed for automatic restoration.

Repair: make initialization create-only/idempotent and prevent ordinary local
review from overwriting an existing paid authorization. Test repeat actions.

### F05 — Medium: an empty territory request is approved and exported

Locations: `src/rightsrelay/models.py:36`, `src/rightsrelay/gate.py:29`,
`src/rightsrelay/app.py:47`.

Territory lists accept zero elements. The gate computes a set difference, so
an empty request finds no unauthorized territories. A real temporary export
with `territories=[]` returned CLEARED_LIMITED and wrote a packet with no
territorial scope. The CLI can produce this through `--territories ''` or a
comma-only value. Other identity/scope strings also lack non-empty constraints.

Repair: reject incomplete release scope before evaluating permission. Add a
regression proving that missing/empty territories never produce a packet,
alongside the existing valid-date and identity cases. Do not infer worldwide
rights from an empty list.

### F06 — Medium: acquisition pays before checking local prerequisites; retries can pay again

Locations: `src/rightsrelay/app.py:240`, `src/rightsrelay/app.py:250`,
`src/rightsrelay/app.py:213`, `src/rightsrelay/x402_buyer.py:118`.

`acquire_grant()` invokes the purchase before recalling the entity. A diagnostic
purchase callback was reached with a nonexistent DB; it stopped there without
any payment. In a real run the buyer can settle before finding that local
authorization cannot be recalled, validated, or written. There is also no
preflight that notices an already sufficient purchased grant, no persistent
pending-acquisition record, and no post-payment recovery path. Repeating the
command initiates another handshake; it is not idempotent.

Entity persistence and journaling are separate writes. A failure after the
entity write may return an error despite an applied grant, while a failure
before it can leave payment complete but the release blocked.

Repair: validate memory/scope before payment, persist the actual purchase
outcome for recovery, and make repeated acquisition resume or return the
existing sufficient grant. Test interrupted and duplicate acquisitions without
using paid network jobs as ordinary unit tests.

### F07 — Medium: signed-grant and REFERENCE evidence requirements are unimplemented

Locations: `src/rightsrelay/x402_seller.py:147`,
`src/rightsrelay/x402_buyer.py:60`, `src/rightsrelay/app.py:259`,
`src/rightsrelay/models.py:24`, `site/index.html:172`.

The seller issues grant JSON and a settlement reference, but no issuer
signature or signed scope. The buyer checks identity strings, dates, scope,
and the parsed settlement response; it does not verify a rights-holder
signature. A payment authorization signature is not a signature over the
license scope. This is a gap against the supplied signed-grant requirement,
not evidence that a payment was fabricated. The configured local seller is
currently a trusted component.

No application path calls `set_reference`. Original grant text, policy schema,
and the purchased grant are not stored in REFERENCE, and the ordinary CLI
flow leaves `evidence_refs` empty. The website nevertheless presents REFERENCE
grant text/static policy as implemented. The payment journal records payment
metadata but not the original signed license document.

Repair: implement the promised issuer-evidence path within the fixed track/
campaign scope, or explicitly disclose what is absent. Keep evidence in Sibyl
REFERENCE with references from the single WARM entity, not a second authority.

### F08 — Medium: the planned live-progress demo cannot work as written

Locations: `src/rightsrelay/console.py:195`,
`src/rightsrelay/console.html:252`, `src/rightsrelay/console.html:268`,
`scripts/record_demo.md:49`.

The async action handler uses synchronous `subprocess.run(capture_output=True)`
without a timeout. This blocks the event loop, buffers all CLI output until
exit, and prevents `/status` from responding during the command. The browser
also explicitly stops polling while an action runs. As a result, negotiation,
escrow, 402, payment, and retry are not visible as they happen. They appear
together after completion in a 94px-high output pane. A hung child can leave
the operator board stuck.

Repair: for the recording, show the existing CLI in a visible terminal beside
the board, or implement bounded nonblocking action execution with progress.
The terminal option is the smallest change needed for an honest filmable take.

### F09 — Medium: the mainnet facilitator prohibition is not enforced

Locations: `src/rightsrelay/x402_seller.py:94`,
`src/rightsrelay/x402_buyer.py:26`, `README.md:247`.

Both settings paths only require a non-empty facilitator when mainnet is
enabled. A configuration-only probe accepted `eip155:8453` together with
`https://x402.org/facilitator`, contrary to the hard constraint and README's
claim that this combination is never used. No network payment was attempted.
Mainnet remains off by default, so this is a configuration guard gap rather
than an observed mainnet payment failure.

Repair: reject the test facilitator under mainnet in the shared configuration
boundary and test the rejection before constructing a payer/server.

### F10 — Medium: submission copy contradicts the implemented partner state

Locations: `README.md:72`, `README.md:250`,
`src/rightsrelay/console.html:155`, `src/rightsrelay/console.html:159`.

The README claims completed mainnet ACP job 78052 in the partner section, then
says no mainnet job is claimed in its limitations. The console labels the ACP
contract as Base Sepolia although its actual URL is Base mainnet. These are
visible judging inconsistencies. Dependency counts in the README are also
stale (15 low versus the current 16).

No final video URL, two public-post URLs, public PMF artifact, or private
submission-ready receipt was found in the checked repository. This does not
prove those artifacts do not exist externally, but their completion was not
verified. The deployed site is a static submission page; it is not the runtime
console and cannot demonstrate fresh-session recall itself.

Repair: align all network/evidence labels, publish/link the final artifacts,
and verify the actual submission status. Keep PMF at zero until evidence exists.

### F11 — Medium: deletion coverage exists locally but is not running in CI

Locations: `tests/test_deletion.py`, `pyproject.toml:13`, repository automation.

There is no active test workflow in the checked main branch. The visible GitHub
runs deploy Pages only. Consequently the requested deletion test is present
and passed locally, but the explicit requirement to run it in CI is unmet.
The workflow-permission issue from the site deployment remains relevant.

Python dependencies use broad ranges and no committed resolution lock, despite
the integration's dependence on inspected versions such as x402 2.21.0 and
Sibyl 0.8.0. A fresh install can differ from this successful audit environment.
The Node side does have a lockfile. Funded x402 testing is gated on credentials
alone, so loading `.env` before ordinary pytest can trigger a payment; README
documents this but there is no independent run-live opt-in as ACP has.

Repair: add an authorized offline CI workflow, with funded credentials absent,
and record/reproduce the verified Python dependency resolution. Add the
failure-path regressions above before relying on test counts as readiness.

### F12 — Medium, offline-grant path: scope merging creates unauthorized combinations

Location: `src/rightsrelay/app.py:215`.

`apply_grant()` independently unions channels and territories, globally ORs
paid media, and applies one expiry. In a probe, an existing organic YouTube/UK
September grant plus an Instagram/US paid October supplement permitted paid
YouTube/US in October. Neither input supplied that combination. The present
fixed x402 seller explicitly grants the complete YouTube+Instagram/UK+US paid
scope, so this does not show that its current grant overauthorizes. It does
affect the exposed narrower CLI supplement demonstrated in the probe.

Repair: for this frozen one-grant model, accept only a complete authoritative
replacement scope compatible with its Cartesian-product representation, or
reject supplements that cannot be represented faithfully. Do not expand into
a general licensing model merely to fix this scoped build.

## Lower-priority observations and practical limits

- `site/404.html:3` uses relative assets and a `./` home link. A deployed nested
  missing URL returned 404 for its resolved stylesheet too; the home link also
  remains in the missing directory. Root-relative assets/home links fix this.
- `src/rightsrelay/console.py:40` and `:51` hard-code September 2 as the release
  date. Demonstrate that historical date honestly rather than calling it
  today's launch; it will not exercise future expiry as the wall clock advances.
- The HTTP action wrapper returns 200 with CLI exit 1 on a blocked request.
  The export exception has `status_code=409`, but no actual HTTP export route
  translates it into a 409 response. This is intentional in current console
  tests; public statements should distinguish a 409-compatible exception from
  an observed HTTP 409 endpoint.
- Export writes the packet directly rather than via an atomic replacement.
  Entity updates use read-modify-write without compare-and-swap. Crash and
  concurrent mutation guarantees are therefore limited; the README already
  restricts concurrent reviewers/grant edits. No concurrency stress test was run.
- `acp_client.py:82` finds ACP assets relative to the source tree; the Python
  wheel does not package the Node project. The documented source-checkout setup
  is the supported installation path, not a standalone pip-installed ACP app.
- The site labels 95.6% as Sibyl's LongMemEval reference, but places it inside
  "Verified implementation evidence." It is not RightsRelay's accuracy result;
  give a source and avoid making it the leading product evidence.
- The console's mobile layout has a minimum width and hides document overflow;
  it is a desktop filming surface, unlike the responsive public site. It does
  not show full authorization JSON, version, or an entity diff as originally
  requested; use CLI status/diff evidence in the recording.

## Hackathon implications

The official rules use one leaderboard, a memory pass/fail gate, then weighted
scoring and verified partner multipliers. They require fresh-session recall
in a continuous unedited video segment, repo write/read pointers, a deletion
test, submission artifacts, and visible partner execution. See
[official rules](https://hack.sibyllabs.org/rules).

| Area | Audit conclusion |
| --- | --- |
| Memory eligibility | Strong code evidence: mandatory Sibyl recall before every new export; deletion test and real restart rehearsal pass. Final video remains unverified. |
| Memory sophistication (40) | Shared mutable entity and separate reviewer are implemented; missing reference evidence and inconsistent journal/display projections weaken the case. |
| Innovation/usefulness (25) | Specific agency release-operations workflow is coherent; no independently verified customer validation was found. |
| Execution (20) | Passing suites support the happy path, but the confirmed failure cases and incomplete ACP fallback reduce confidence. |
| Pitch (15) | Storyboard exists; buffered output, incorrect network labels, and absent full entity/diff need attention before filming. |
| PMF (+10) | No verified artifact found; forecast zero, not an invented bonus. |
| Partner multiplier | Historical real-job/settlement evidence is recorded. No new funded run was done; final demo visibility and judges' verification determine the multiplier. |

The rules inspected do not explicitly resolve Base Sepolia eligibility. Obtain
organizer confirmation or submit the disclosed evidence without promising
that the multiplier is guaranteed. The public website alone does not satisfy
the mandatory recorded runtime demonstration. A historic ACP job identifier
alone is weaker than demonstrable lifecycle and shared-memory evidence.

## Recommended sequence

1. Repair F01–F03 and add regressions at the actual completion/action/status
   boundaries; these are the most consequential findings.
2. Guard reset/review and empty scope; add payment preflight and recovery tests.
3. Reconcile submission copy/evidence and make the take filmable using the CLI.
4. Address signed/reference evidence and offline CI, or document remaining
   limitations honestly instead of claiming them complete.
5. Rehearse again from an isolated DB after the repairs, record the continuous
   kill/recall beat, link the video/posts, and verify submission readiness.

This is an audit report, not authorization to change frozen policy or send
another funded transaction. Repairs should follow the user's next instruction.
